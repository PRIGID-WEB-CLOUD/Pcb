# LUXE BOUTIQUE — Full App Audit: What's Missing or Incomplete

Scanned every page, every route file, and cross-referenced frontend fetches against backend logic. Organized by severity, not by feature area, because some of these are security bugs, not "nice to haves."

---

## 🔴 Critical — money/security bugs, not just missing features

### 1. Checkout trusts the client for price
`POST /api/payments/initialize` (`routes/payments.ts`) takes `amount` directly from the request body and sends it to Paystack/Flutterwave. Nothing recomputes it server-side from the actual cart contents and current product prices in the DB. Anyone who can call the API directly can pay $1 for a $500 order.

### 2. Order creation also trusts the client for price
`POST /api/orders` (`routes/orders.ts`) takes `total`, `price`, and `discountAmount` straight from the request body. No server-side cross-check against real product prices or the coupon's actual discount.

### 3. Hardcoded payment-bypass left in checkout
In `CheckoutVerifyPage.tsx`, the success check is:
```
reference.startsWith("demo_")
```
Any reference beginning with `demo_` is treated as a successful payment, no gateway verification needed. This needs to be removed entirely before going live, not just gated behind an env flag.

### 4. Stock is never decremented
Products have a `stock` column, but no route anywhere in `api-server` reduces it after an order is placed. Selling 50 of an item that only has 5 in stock is fully possible. There's also no out-of-stock check at checkout.

### 5. Generated API keys do nothing
`AdminSettingsPage` / `apikeys.ts` lets an admin generate API keys, but no middleware in the entire app actually validates an incoming request against the `apiKeys` table. It's a vanity feature — the keys can't be used for anything yet.

## 🟠 High — features that visually work but the backing system doesn't exist

### 6. No order confirmation email
`lib/email.ts` has functions for OTP, password reset, team invites, and newsletter campaigns — but nothing for "your order has shipped" or "we received your order." A customer gets no email after checkout at all.

### 7. Twitter Queue doesn't post itself
Tweets land in `twitter_tweet_queue` with a `scheduledFor` time, but nothing reads that table and posts at the right time. No cron/worker exists anywhere in the codebase.

### 8. Twitter Auto-post Rules don't fire
`twitter_auto_rules` (trigger → action mappings like "new arrival → tweet") are just an on/off DB toggle. No logic watches for store events and fires a rule.

### 9. WhatsApp Journeys are a switch, not a journey
`whatsapp_journeys` toggles active/inactive but there's no step engine — no logic ever sends step 1, waits, sends step 2, etc. `sentCount`/`convRate` shown in the UI are static seed values, not computed from real activity.

### 10. WhatsApp opt-in/out keywords aren't enforced
`whatsapp_optin_settings` stores the keywords, but the webhook receiver that gets inbound messages doesn't check incoming text against them or maintain a real opted-in/out contact list.

### 11. Dropshipping providers are mostly fake "connect" checks
In `providers.ts`: Printful's connect button does ping a real API. ShipBob and Gooten just check `apiKey.length > 4`. Eprolo checks `apiKey.length > 8`. None of the four ever actually syncs an order to the provider for fulfillment — "connect" is the entire feature; there's no order-forwarding logic anywhere.

## 🟡 Medium — partial/cosmetic gaps

### 12. Facebook Pixel tab is config-only
Toggling pixel events saves a DB row but never fires an actual `fbq('track', ...)` call anywhere on the storefront.

### 13. Facebook Custom Audiences are local-only
Creating an "audience" in the Facebook channel page writes to a local table with a fabricated size string (e.g. "Building…", "4,820") — no call to Meta's real Custom Audiences API.

### 14. Reviews have no moderation
Customers can post a review and it shows immediately — no approve/reject step, no edit, no delete, no spam/abuse handling.

### 15. `sendPasswordResetEmail` is dead code
`lib/email.ts` defines both `sendPasswordResetEmail` and `sendCustomerResetEmail` — only the latter is actually called from `auth.ts`. Redundant function, minor cleanup.

## ✅ Confirmed genuinely working (so you don't waste time re-checking these)

- Facebook/Instagram/Twitter posting, Meta Catalog sync, Meta Ads insights/campaigns/account, Instagram media/publish — all real Graph API calls, reachable via their dedicated pages (`AdminInstagramPage`, `AdminMetaAdsPage`, `AdminMetaCommercePage`, `AdminSocialAnalyticsPage`)
- Paystack/Flutterwave payment initialize + verify (real calls to both gateways — just missing the server-side amount validation noted above)
- Newsletter campaigns — real SMTP sending via nodemailer, with graceful "logs to console" fallback when SMTP isn't configured
- Team invites — real emails sent, role-based permissions enforced (`requireRole`)
- Coupons — validated server-side at checkout, just not cross-checked against the final charged amount (see #2)
- Media/Cloudinary uploads — real
- Reviews — real read/write and properly joined into product pages (just no moderation, see #14)
- Customer password reset — real email flow
